# Correctness review of flyology-ada/flyology-object-storage

Run a complete correctness review of `flyology-ada/flyology-object-storage`, verify every
finding with a runnable reproduction, file the confirmed findings as GitHub issues in the
established house style, and prepare a triage brief for Codex. This repeats the procedure used on
`flyology-ada/flyology-postgres` (issues #31 to #93, filed 2026-09-05) and before that on
`flyology-ada/flyology` (issues #105 to #197). Use Fable subagents for discovery and other
high-level thinking, Opus subagents for verification, drafting and other routine work.

## Scope and partition

`src/` is about 257,000 lines, and `src/flyology-object_storage-s3-model.adb` alone is 79,000
generated lines (from the pinned botocore S3 model through `tools/generate-s3-model.py` and
`tools/s3_codegen.py`). Do not read generated packages line by line; review their generator and
sample their output through differential checks. Prioritise the surfaces where a defect is
severe: attacker-controlled parsing, signature verification, filesystem atomicity and path safety,
server routing and authorisation, multipart and versioning state. Propose about twelve discovery
areas along these lines and adjust after reading the tree:

- WIRE: `s3-wire_core`, `s3-xml`, `s3-xml_writers`, `s3-strict_xml_codecs`, `s3-requests`,
  `s3-core`, `s3-imf_dates` (the SPARK boundary; bounds, entity safety, range parser, decimal and
  size scalars, request-target classification, date parsing).
- SIGV4: `s3-sigv4`, `s3-sigv4_encoding`, `s3-sigv4_verification`, `server-authentication`,
  `server-static_credentials`, `server-mfa`, `secrets` (canonicalisation against the AWS test
  vectors, timestamp windows, presigned URLs, chunked and trailer signing, constant-time
  comparison, credential scope, header ordering and duplicate-header rules).
- CHECKSUM: `s3-checksums`, `s3-checksum_crc`, `s3-checksum_policy`, `checksum_engine`, the
  xxhash C shim (all ten algorithms, composite and full-object modes, canonical base64, trailers).
- CLIENT-LOW: `client-low_level` (request building, response and error parsing, retry and
  redirect behaviour, header canonicalisation).
- CLIENT-BUCKETS and CLIENT-OBJECTS: `client-buckets`, `client-objects`, the bounded and paginated
  REST/XML read families and mutations (pagination cursors and markers, typed outputs, error
  outcomes, non-replay guarantees, conditional headers).
- TRANSFERS: `client-transfers` and `s3-multipart` (part sizing, the 10,000-part and 50 TiB
  bounds, range arithmetic, resume, part checksums, concurrency and cancellation).
- MODEL: the generator and its verifiers under `tools/` (logic that would be wrong in every
  generated descriptor: enum mapping, member locations, XML traits, required-member handling).
- BACKEND-MEMORY: `backends-memory`, `backends.ads`, `backends-listing`, `bucket_listing`,
  `multipart_listing` (capacity reservations under concurrency, listing semantics for delimiter,
  prefix, start-after, continuation tokens, key and version markers, common prefixes, conditional
  writes, versioning states, multipart lifecycle, delete markers).
- BACKEND-FILES: `backends-files`, `durability`, the durability and secure-erase C shims
  (atomic publication, key path encoding, symlink and traversal safety, fsync ordering and crash
  consistency, partial writes, rename semantics, supplied ETag handling).
- BACKEND-SQLITE: `sqlite/` (catalogs, migrations, transaction boundaries, the versioning merge
  `CASE` update, reopen behaviour).
- SERVER: `server-s3_applications` and the `server/` executable (request classification and
  routing, error XML and status codes, authorisation policy, conditional and range responses,
  chunked uploads, multipart on the server side, session and credential handling, signals).
- S3-DOMAIN: the per-operation typed codecs (`s3-acl`, `lifecycle`, `replication`,
  `notifications`, `versioning`, `versions`, `listings`, `object_lock`, `intelligent_tiering`,
  `inventory`, `analytics`, `metrics`, `logging`, `website`, `encryption`, `annotations`,
  `attributes`, `tagging`, `deletions`, `copies`, `buckets`, `bucket_controls`,
  `metadata_configurations`, `metadata_tables`, `errors`), compared with the pinned botocore
  model under `vendor/` and the qualification documents under `docs/qualification/`.

Reference material for interop claims: the pinned botocore model (source of truth for shapes),
the AWS S3 API reference and the SigV4 specification (cite by document and section), the
executable compatibility matrix `docs/compatibility/s3.md` (what the repository claims), and,
where Docker is available, real MinIO, RustFS and SeaweedFS servers driven by the repository's
own scripts. A claim about what AWS does that you cannot check against the model or a real
server must say so.

## Severity rubric

- P0: memory or aliasing unsafety, security-relevant (signature verification bypass, path
  traversal or symlink escape, credential or secret exposure, authorisation bypass), data loss
  or durability violation (an acknowledged write that is not durable or is silently corrupted),
  hang or deadlock in normal operation, or an interop-breaking protocol violation that a stock
  client (aws-cli, boto3, MinIO client) or server rejects.
- P1: wrong result or unexpected exception on valid input via a reachable path, or a documented
  contract violated (`.ads` comment, README, compatibility matrix, qualification document).
- P2: edge-case incorrectness, wrong diagnostics, or contract drift needing unusual input.

Documented policy values (limits, defaults, capacities) are not bugs unless they break a protocol
rule or a documented invariant; report them separately under "Observations not counted".

## Phase 1: discovery

One Fable subagent per area, read-only, launched in batches of at most four (the Fable limit
was hit with nine at once; if an agent dies on a rate limit, relaunch it, and fall back to Opus
if the limit persists). Each agent writes `review/discovery-<AREA>.md` incrementally, creating
the file after its first finding so a crash preserves partial results, and rewrites the header
at the end. Report format: scope; the rubric; a summary table (ID, title, severity, confidence);
per finding `### <AREA>-<n>: <title>` with Location (file:line), Severity, Confidence, Evidence
(exact quoted lines), Failure scenario, Reproduction test sketch (concrete calls and inputs,
expected versus actual, expressible through the public API or the in-memory backend without
external services where possible), Existing coverage; then "Areas reviewed with no findings"
and "Observations not counted". Instruct each agent to read the `.ads` contracts first, to
check reachability through real callers, and to try to refute each candidate itself.

## Phase 2: adversarial verification

One Opus subagent per area. It must try to refute each finding against the source (and the
model, the real servers or the AWS documents where relevant), and for every finding that
survives write a reproduction program under a harness and run it. Verdicts: CONFIRMED, REFUTED,
PARTIALLY CONFIRMED, DOCUMENTED LIMITATION, UNVERIFIABLE; corrected severity with the rubric;
a one-paragraph description. Report to `review/verification-<AREA>.md` with sections
`### <ID>: <title>` and fields Verdict, Severity, Repro, Output, Description.

Harness: build `tests/repros` (an Alire crate pinned to the root crate, plus one for `sqlite/` if
needed) following the postgres pattern. Provide support for the three levels a spike needs: direct
calls into a package; the memory backend and the S3 application over an in-process Flyology HTTP
loopback server (see how `tests/src` starts `s3_memory_server` and `s3_files_server`); and, for
interop claims, the Docker-backed servers through the repository's scripts. A spike asserts the
correct behaviour and must print `BUG REPRODUCED` and exit 1 on current sources. Every confirmed
finding gets one program; a finding only reachable through a running server or Docker is
verified that way with a bounded timeout, and the report says so. After all verifications, run
`run-all.sh` in every harness so the evidence table is one clean sweep.

Verifiers may raise new findings they trip over; give them the next number in that area (as the
postgres review did with a `-8b`) and verify them the same way.

## Phase 3: consolidation

Write `FINDINGS.md` at the worktree root mirroring the postgres one: scope and method, the
rubric, how to reproduce, a totals table per area, an index table (ID, severity, title, location,
repro), per-area sections with Severity, Location, Repro, What is wrong, Notes (maintainer
decisions needed, tests that assert the current wrong behaviour, refuted sub-claims,
duplicates), and appendices with per-area coverage evidence and the artifact list. Copy every
discovery and verification report into `review/`. Sweep every repro once more and record the
result. Report totals honestly, including what could not be exercised (no AWS account; Docker
servers absent, if so).

## Phase 4: issue bodies and filing

- Draft one body per confirmed finding into `review/filing/<ID>.md` using `STYLE.md`, with Opus
  subagents, one per area. Each body re-runs its repro for fresh output, verifies every file:line
  with `sed -n` at the reviewed commit, cites the model, the AWS document or the real-server
  behaviour it relies on, folds duplicates into the primary issue, uses `{{ISSUE:<ID>}}` for
  cross-references, names any existing test that asserts the wrong behaviour, and says "This
  needs a maintainer decision" with the options wherever a fix adds a public constant, variant,
  parameter or default (the "Decision authority" and "Ada interface values" sections of
  `AGENTS.md`). Label `bug`; add `documentation` only for pure contract drift. No internal IDs,
  no mention of the review, agents, Claude, the harness directories or `FINDINGS.md` in any title
  or body. Refer to repository rules by `AGENTS.md` section, never by `.claude` path.
- Validate with `file_issues.py --dry-run` until every body passes.
- Stop and ask the user before filing (this is an outward-facing action on a public repository):
  show two sample bodies and the totals, and ask three things at once: file all or only P0 and P1;
  push the review branch with the harnesses or keep them local (the postgres review kept them
  local, so the issues had to be self-contained); the lane order for the brief. Then file with
  `file_issues.py --file` (paced, in dependency order), run `--resolve` to patch forward
  references and to substitute issue numbers into the brief, and check the list on GitHub
  (count, labels, no leaked IDs).
- Record the finding-to-issue mapping in `review/ISSUES.md` and in a project memory note, as the
  postgres review did.

## Phase 5: triage brief for Codex

Write `review/TRIAGE_FOR_CODEX.md` mirroring the postgres brief: ground rules citing `AGENTS.md`
sections ("Flyology Object Storage agent guide", "Decision authority", "Ada interface values",
"Ada source style", "Review cycle", "Commits", "Repository workflow", "TLA+ assurance",
"Performance testing") and the verification commands (`tools/ci/run-tests.sh`,
`tests/scripts/test.sh`, `sqlite/tests/scripts/test.sh`, `tools/prove.sh` for anything under the
SPARK boundary with its nine forced units, the botocore model verifiers, the Docker conformance
scripts for interop items, `git diff --check`, the maintained formatter on handwritten Ada, and
the generated-source rule: change `tools/generate-s3-model.py` or its input, regenerate, and let
the verifiers check); one issue per PR with `Closes #N`, Problem/Solution commits, no attribution
footers; regression tests placed in the existing suites and corpora; "Confirm every finding before
fixing it" (re-read at current `main`, rebuild the spike, drive a real S3 client or server where
the harness has one, report disagreements to the master); "Work organization" (one master task,
lanes of at most three in separate worktrees, serialized Alire and Docker runs, reports after
every merged PR, DECISIONs through the master); "Model first" aligned with the "TLA+ assurance"
section (SPARK contracts inside the proof boundary; bounded TLA+ models with a `_broken`
configuration for the multi-step state machines such as multipart lifecycle, versioning
transitions and listing pagination, with TLC and TLAPM both and replay through the shared
`flyology-ada/tla` harness); then the layered issue lists, P0 before P1 before P2, each entry
with the issue number, the one-line fix direction, dependencies, and DECISION or MODEL FIRST
tags; and an "Explicitly out of scope" section for unrelated open PRs and issues. Propose a
layer order that puts the surfaces stock clients and servers hit first (wire and SigV4, then
server, then backends, then client families, then domain codecs), and let the user change it.

## Final report to the user

Lead with the outcome (confirmed counts by severity and area, the P0s in one line each), then
what was not exercised, then where everything lives (FINDINGS.md, review/, harnesses, issue
range, brief), then the maintainer decisions the fixes need. Keep the user's own rules for
communication: short sentences, no em-dashes, no hedging about verified facts, and a plain
statement of anything that failed or was skipped.

## Pitfalls seen in the postgres run

- Nine Fable discovery agents at once hit the Fable rate limit; eight died mid-review. Batch
  them, and have every agent write its report incrementally.
- `SendMessage` to an existing subagent may be disabled; spawn a fresh agent with the context
  it needs instead.
- The Bash tool's working directory persists between calls; a bare `cd review/filing` can fail
  when you are already there. Use absolute paths.
- A subagent may be refused when asked to write a findings or report `.md` file; if so, have it
  return the content and write the file yourself, or extract the text from its transcript with
  a script that writes straight to disk (never dump a subagent transcript into your context).
- Pace `gh issue create` (about six seconds apart) and retry on secondary rate limits; the
  postgres run filed 63 issues in about nine minutes without an error.
- The issue-body validator must not forbid legitimate domain words (the postgres run first
  flagged "verifier", a SCRAM term) and must exempt `.claude` inside a path only when the path is
  the subject; in the end no `.claude` reference belongs in an issue or in the brief at all.
- Several severities moved during verification, both up (a "no denial of service" claim was
  refuted by measurement; a retention-floor bug turned out to discard live WAL) and down
  (policy values in a public spec were relabelled as maintainer decisions). Expect the same and
  keep the verifier's corrected severity, with the discovery severity noted.
