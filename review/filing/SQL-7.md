Title: Grammar-level ereport diagnostics keep the raw %s format and report the wrong cursor
Labels: bug
Refs: none

## Summary

The action generator translates a `gram.y` `ereport` into a raised exception carrying the `errmsg` format literal only, dropping every `%s` and `%d` argument and the `parser_errposition(@n)` argument. The engine then reports that message at the location of whatever lookahead token finished the production. A user of the library sees `%s constraints cannot be marked DEFERRABLE` where PostgreSQL says `CHECK constraints cannot be marked DEFERRABLE`, and sees a cursor pointing at the wrong token for every grammar-level `ereport`, including the ones that take no arguments.

## Problem

Commit `6f496f5`.

The generator turns a `DoStmt` containing an `errmsg` call into a raise carrying the first `errmsg` argument (`sql/tools/generate_native_actions.py:600-609`):

```python
        if kind == "DoStmt":
            messages = [
                item for item in walk(node)
                if item.get("kind") == "CallExpr" and referenced_name(children(item)[0]) == "errmsg"
            ]
            if messages and len(children(messages[0])) > 1:
                message = self.expression(children(messages[0])[1])
                return [f"{indent}raise Semantics.Parser_Error with Semantics.Text_Of ({message});"]
```

Only the format literal survives. The generated result for the `LIMIT` rule (`sql/src/flyology-postgres-sql-native-action_catalog_chunk_08.adb:735-736`, generated by `tools/generate_native_actions.py`, not hand-edited):

```ada
               raise Semantics.Parser_Error with Semantics.Text_Of (Builders.Text
                  ("LIMIT #,# syntax is not supported"));
```

and for `processCASbits` (`sql/src/flyology-postgres-sql-native-action_helper_catalog_chunk_01.adb:731-732`):

```ada
                     raise Semantics.Parser_Error with Semantics.Text_Of (Builders.Text
                        ("%s constraints cannot be marked DEFERRABLE"));
```

The grammar supplies both the argument and the position. For the `LIMIT` rule (`sql/backends/v18/vendor/native_source/backend/parser/gram.y:13310-13318`):

```c
			| LIMIT select_limit_value ',' select_offset_value
				{
					/* Disabled because it was too confusing, bjm 2002-02-18 */
					ereport(ERROR,
							(errcode(ERRCODE_SYNTAX_ERROR),
							 errmsg("LIMIT #,# syntax is not supported"),
							 errhint("Use separate LIMIT and OFFSET clauses."),
							 parser_errposition(@1)));
				}
```

For the `CHECK` constraint the argument is passed to `processCASbits` (`sql/backends/v18/vendor/native_source/backend/parser/gram.y:4203-4213`):

```c
			CHECK '(' a_expr ')' ConstraintAttributeSpec
				{
					Constraint *n = makeNode(Constraint);

					n->contype = CONSTR_CHECK;
					n->location = @1;
					n->raw_expr = $3;
					n->cooked_expr = NULL;
					processCASbits($5, @5, "CHECK",
								   NULL, NULL, &n->is_enforced, &n->skip_validation,
								   &n->is_no_inherit, yyscanner);
```

and used in the `ereport` at `sql/backends/v18/vendor/native_source/backend/parser/gram.y:19466-19471`:

```c
			ereport(ERROR,
					(errcode(ERRCODE_FEATURE_NOT_SUPPORTED),
			/* translator: %s is CHECK, UNIQUE, or similar */
					 errmsg("%s constraints cannot be marked DEFERRABLE",
							constrType),
					 parser_errposition(location)));
```

The other two templates in the spike are at `sql/backends/v18/vendor/native_source/backend/parser/gram.y:1283-1286` (`unrecognized role option "%s"`) and `sql/backends/v18/vendor/native_source/backend/parser/gram.y:17079-17082` (`unrecognized JSON encoding: %s`). The same pattern covers roughly ten templates in the grammar, including `column number must be in range from 1 to %d` and the other `processCASbits` variants.

The engine reports the raised message at `Last_Location` with no context, and never at the location the `ereport` named (`sql/src/flyology-postgres-sql-native-engine.adb:128-129`):

```ada
         else
            Report_Error (Error, Last_Location, False);
```

`sql/README.md:320-322` comes close to promising PostgreSQL-identical diagnostics for exactly this surface:

```text
The comparison is member-order independent for objects and order sensitive for
sequences. It preserves scalar kinds, enum values, omitted fields, array
contents, parse validity, diagnostics, and cursor positions.
```

The comparison that sentence describes never runs on this input. The regression corpus check compares only statements the oracle accepts (`sql/tests/src/flyology-postgres-sql-regression_corpus_testing.adb:183-185`, :256-257), so a statement that raises a grammar-level `ereport` is counted as rejected and skipped. The native-versus-oracle corpus has four invalid statements (`sql/tests/src/flyology-postgres-sql-differential_testing.adb:69-75`) and none of them reaches a grammar-level `ereport`. The owned corpus compares the owned result against `Parse_Baseline`, which runs the same generated actions, so both sides carry the same format string and the same cursor.

The expected cursor is major-dependent. For the `processCASbits` and JSON templates the pinned oracle carries cursor 0 on PostgreSQL 14 through 17 and a real cursor on PostgreSQL 18, so the size of the divergence differs by major even though the native cursor is wrong everywhere.

## What should happen

A grammar-level `ereport` must produce the formatted message with its arguments substituted, `CHECK constraints cannot be marked DEFERRABLE` rather than `%s constraints cannot be marked DEFERRABLE`, and must report it at the location the `parser_errposition` argument names, cursor 10 for `SELECT 1 LIMIT 1, 2`. A raw printf format string must never reach `Diagnostic_Message`.

## Suggested treatment

The defect is in `sql/tools/generate_native_actions.py:600-609`, and the affected packages under `sql/src` are generated by it and are not hand-edited in this repository. The generator already has the whole `ereport` call in hand, so both dropped pieces can be recovered there:

- take the remaining `errmsg` arguments, translate them as ordinary expressions the way other call arguments are translated, and emit a formatting call so the raised message carries the substituted text;
- take the `parser_errposition` argument, translate the `@n` location the same way the generated actions already translate `Locations (n)`, and emit it alongside the message.

Carrying the position through requires a way to raise a parser error with an explicit location. The engine currently derives the position from `Last_Location` for this exception class (`sql/src/flyology-postgres-sql-native-engine.adb:128-129`), and `Failed_At` already exists for the scanner-parser path a few lines above. This needs a maintainer decision on the mechanism: extend `Semantics.Parser_Error` handling so a generated action can set the failure location before raising, or introduce a distinct exception that carries the location, or encode the location in the exception message and strip it in the engine. Whichever is chosen, every affected major must be regenerated and the second generator run must change no files.

The regression test belongs in `sql/tests/src/flyology-postgres-sql-differential_testing.adb` beside the existing invalid statements at lines 69-75, as `Check ("SELECT 1 LIMIT 1, 2")` on all majors and `Check ("CREATE TABLE t (a int, CHECK (a > 0) DEFERRABLE)")` on all majors. The spike is that test. No existing test asserts the current behaviour.

## Severity

A raw printf format string reaches the public `Diagnostic_Message` for roughly ten grammar templates, and the cursor is wrong for every grammar-level `ereport`, including argument-free ones. Any application that shows the parser's diagnostic to a user shows `%s` where PostgreSQL names the construct, and any application that underlines the offending token underlines the wrong one. The input is invalid on both sides, so no valid statement is misparsed. The expected cursor differs by major for the `processCASbits` and JSON templates, where the pinned oracle reports 0 on PostgreSQL 14 through 17 and a real cursor on PostgreSQL 18. All five supported majors; the JSON template exists from PostgreSQL 16.
